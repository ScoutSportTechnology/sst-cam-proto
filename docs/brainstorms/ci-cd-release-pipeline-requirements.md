# CI/CD & Release Pipeline — Requirements (sst-cam-proto)

**Date:** 2026-06-10
**Status:** Ready for planning
**Type:** Standard — infrastructure / DevOps
**Cross-repo note:** Part of a shared CI/CD effort across sst-cam-app, sst-cam-firmware, sst-cam-proto. This doc covers the **proto** slice; governance below is duplicated in each repo because it applies to each.

## Problem

No automated CI or release flow. Protocol changes ship as raw submodule SHA bumps with no breaking-change gate, and consumers run codegen themselves. Need lint → test → release automation, breaking-change detection, and a published, versioned SDK.

## Goals

- `main` default, PR-gated, immutable semver tags.
- PR runs **`buf lint` + `buf breaking`**; merge blocked until green.
- Automated semver releases (no hand-cut tags).
- On release: **publish a versioned SDK** so the app stops vendoring proto as a submodule.

## Non-Goals (now)

- C++ SDK publishing — firmware keeps the git submodule. Only the app moves to the SDK.

---

## Branch & Tag Governance (shared, applies here)

### Branch ruleset (`main`)
- `main` = default; feature branches unrestricted, per-developer.
- Require PR; **1 approval**; dismiss stale reviews on push; require thread resolution.
- Block force-push (`non_fast_forward`) + deletion.
- **Add `required_status_checks`** = `buf lint` + `buf breaking` jobs, once workflows exist.

### Tag ruleset (`v*`)
- Semver regex: `^v\d+\.\d+\.\d+(-[0-9A-Za-z.-]+)?(\+[0-9A-Za-z.-]+)?$`.
- Immutable: block `update`, `deletion`, `non_fast_forward`.
- **Bypass actors:** `OrganizationAdmin` + the org **GitHub App** (added via GitHub UI, not JSON — UI resolves the App name to its numeric `actor_id`; a string id fails import with "invalid actor").

### Release mechanism (shared)
- **release-please** (PR-based): conventional commits on `main` → release PR → merge bumps semver, tags, cuts GitHub Release.
- **Identity:** one org-owned **GitHub App**, installed on all 3 repos; its token pushes tags and is the tag-ruleset bypass actor. Chosen over `GITHUB_TOKEN` because the default token's recursion guard means its tag push would **not** trigger the release/publish workflow.
- Requires conventional-commit discipline on `main`.

## Proto-Specific Requirements

- **PR CI:** `buf lint` + `buf breaking` (against `main`) — catch breaking protocol changes before merge.
- **Release (on release-please tag):** run codegen and **publish the SDK** + tag the protocol version.

### SDK publishing (fully specified — not deferred)

> **Correction (2026-06-10, planning):** the app is **Flutter/Dart**, not Kotlin/Android. The SDK is therefore a **Dart package distributed by git tag** (app depends via `git: ref: vX.Y.Z, path: gen/dart`), generated by buf (`protoc-gen-dart`). **GitHub Packages Maven and Kotlin/Java below do not apply** and are superseded. See `docs/plans/2026-06-10-001-feat-ci-cd-release-pipeline-plan.md`.

**What it replaces:** today the app embeds proto as a **git submodule** pinned to a SHA and runs protoc/codegen at app build time — requires toolchain + plugins in the consumer, codegen every build, loose SHA versioning.

**Target design:**
- Proto CI runs codegen **once** on release and publishes a **prebuilt, versioned package**.
- **Registry:** **GitHub Packages (Maven)** — same org, private, free, native to the app's Gradle build.
- **Language:** Kotlin/Java bindings for the Android app.
- **Versioning:** SDK artifact version = this repo's release-please semver tag (e.g. `com.sst:cam-proto:1.2.3`). Proto version and SDK version are the same number.
- **Consumption:** app declares `implementation "com.sst:cam-proto:<version>"` — no submodule, no protoc, no codegen in the app.

| Dimension | Submodule (today) | SDK (target) |
|---|---|---|
| protoc/toolchain in consumer | required | not required |
| version identity | git SHA | semver |
| build speed | codegen every build | prebuilt, cached |
| breaking-change gate | manual | `buf breaking` in proto CI |
| coupling | tight (source) | loose (versioned artifact) |

**Mixed consumers:** only the **app** moves to the SDK. **Firmware keeps the submodule** (C++ codegen, no clean packaging story, no near-term need). So proto serves both — published Maven SDK for app, submodule source for firmware.

## Success Criteria

- PR to `main` can't merge until `buf lint` + `buf breaking` pass and 1 review approves.
- Tags only exist if semver; releases immutable.
- Merging release-please PR publishes `com.sst:cam-proto:<semver>` to GitHub Packages, no manual tagging.
- App can resolve and build against the published SDK; firmware submodule unaffected.

## Dependencies / Assumptions

- CI = GitHub Actions.
- Org GitHub App created + installed + added as bypass actor (org-admin task).
- Conventional commits on `main`.
- buf/protoc plugins can produce Kotlin/Java bindings.
- GitHub Packages Maven write access for the publish job.

## Open Questions (for planning)

- Maven `groupId`/`artifactId` naming (coordinate with app).
- `buf breaking` baseline ref (against `main` HEAD vs last release tag).
- Whether to also publish a source jar / multiple language targets later.
